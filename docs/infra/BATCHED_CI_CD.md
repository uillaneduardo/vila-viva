# Integração automática e deploy em lote

## Operação
- Desenvolva em branches internas, PRs destinadas à main. CI individual obrigatório: workflow vnext-ci completo e bem-sucedido no SHA exato da PR.
- Autorize a fila com revisão APPROVED no SHA exato por membro/colaborador/proprietário, ou label **batch:ready** aplicada por mantenedor. A label é autorização persistente da PR (inclusive revisões posteriores, que sempre precisam de CI novo); remova para revogar. Solicitação de mudanças vigente bloqueia. PRs draft, forks e PRs não autorizadas ficam fora.
- Dependência explícita em linha própria no corpo: Depends-on: #123. Dependência deve estar merged ou elegível; ciclos ficam fora. Ordem topológica, número crescente entre independentes. Conflito interrompe lote sem alterar main; corrigir a PR antes de reenfileirar.
- A cada 5 minutos, GitHub Actions agenda integration-batch.yml. A branch integration é exclusiva da automação e reconstruída a partir de main + PRs selecionadas. Aguarda 300 s sem mudança no conjunto elegível; revalida conjunto, SHAs e main, roda CI completo via workflow reutilizável vnext-validation.yml no SHA candidato em runner hospedado, sem segredos nem deploy, e revalida imediatamente antes de promover. Alterações durante a janela ou validação adiam a promoção para o próximo ciclo. Cron do GitHub é best-effort e pode atrasar; não promete exatamente 5 min de relógio.
- Promoção fast-forward em main, nunca force-push em main. A branch integration é descartável e só recebe force-with-lease. Os merges preservam ancestrais das PRs (GitHub pode fechar automaticamente PRs alcançáveis). O GITHUB_TOKEN não gera novos runs por push: o orquestrador dispara explicitamente vnext-ci via workflow_dispatch com SHA esperado, evitando dois deploys. Este segundo CI valida novamente por segurança.
- Merges diretos em main continuam suportados: CI + espera de 5 minutos + checagem de HEAD antes de publicar; versões superadas são ignoradas. Deploy já iniciado não é cancelado; há exclusão mútua no runner e nova checagem de HEAD antes de tocar o host. Se houver push durante um deploy iniciado, podem existir dois deploys.
- Manual: Actions > Oturo integration batch > Run workflow (main), promote_now=true ignora somente a espera, não validação. Para publicar main sem lote, Actions > Oturo vNext CI and homelab2 deploy > Run workflow (main), expected_sha opcional. Se dispatch falhar após promoção, este é o procedimento de recuperação.
- Telegram: Settings > Secrets and variables > Actions: TELEGRAM_BOT_TOKEN e TELEGRAM_CHAT_ID. Notificações de lote promovido/falha e release concluído/falha. Ausência de segredo ou erro de envio não bloqueia publicação. Não enviar tokens em PR.
- Rollback: preservar compose anterior e SHA/tag registrada; qualquer falha após troca do Compose, incluindo teste público, tenta restaurar serviço web anterior e checa localmente. Não reverte automaticamente dados/journal nem apaga volumes. Primeira instalação sem release anterior não permite rollback. Não cancelar manualmente durante deploy; interrupções forçadas ou falha de host podem exigir recuperação manual.
- Configuração: habilitar Actions e permissões de escrita de contents/actions para os jobs declarados; se regras de proteção impedirem fast-forward de main pelo bot, não contornar: usar aprovação/promoção manual ou configurar identidade de integração autorizada. Mudanças em workflows podem exigir permissão workflows:write que GITHUB_TOKEN não possui; nesses casos integrar manualmente. Criar label batch:ready no repositório.
- Segurança: não executar código candidato em job privilegiado; validação em runner GitHub com contents:read; runner self-hosted somente para release main validada. Não incluir secrets na validação de candidato.
- Testes: tests/batch-integration.test.mts cobre autorização, SHA, CI, dependências e janela; workflow CI executa todos os testes e image smoke. Homologar com duas PRs triviais autorizadas, verificar uma promoção, um dispatch, um deploy; simular erro de health em ambiente descartável e conferir rollback e Telegram. Não testar rollback destrutivo em produção.
